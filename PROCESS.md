# The coordinator's process

The steps a coordinating session runs to write a book: the batches, the second reader, theme pages, the illustration, and the review of these instructions. Read `AUTHORING.md` first; the standard a chapter is held to is `STANDARDS.md`, a theme page's or guide's is `PAGES.md`, and how the site's code and each check work is `DEVELOPMENT.md`. Every script prints its usage when run with no arguments.

## Writing a book in batches

A chapter's five steps, and the models, are in `AUTHORING.md` (“Plan for the next book”); which script each agent runs is in `.claude/agents/chapter-*.md`. Finish each step before starting the next (`AUTHORING.md`, “One stage at a time”).

**A batch, in order:**

1. **Write and check: `.claude/workflows/write-chapters.js`**, by name or with `scriptPath`. `args`: `book`, `chapters` (about twelve), `writerModel` (`opus` by default), `models` (finished chapters of the book to imitate), `focus` (the author's questions, by chapter number), `skipKeys` (the source keys whose rows the checker reads without page context). Each chapter goes to a `chapter-writer`, then a `chapter-checker`. The agents leave working files in `.cache/batch/<book>/` (not committed): `proposed/NN.yaml`, the `sources.yaml` entries a chapter needs, and `reports/NN-writer.md` and `reports/NN-check.md`. If the usage limit or a restart stops the run, `resumeFromRunId` with the same `args` skips finished agents; after a single failure, run it again with only the unfinished chapters.
2. **Codex reads the drafts, from the shell: `node scripts/codex-read.mjs <book> <from>-<to> --batch`** (“The second reader,” below). It writes `reports/NN-NN-codex.md`, the batch read side by side, and `reports/NN-codex.md` for each chapter.
3. **Review: `.claude/workflows/review-chapters.js`.** `args`: `book`, `chapters`, `across` (the batch Codex read side by side, when `chapters` is only part of it), `reviewerModel` (`opus` by default), `models`, `lastBatch` (`true` when these chapters finish the book), `themes` (`false` for a book the author has said needs no theme pages; then run `batch-finish.mjs` with `--no-themes` too). One `chapter-reviewer` per chapter decides the checker's findings and Codex's and repairs the chapter once; what a real gap needs it adds only from a source it reads, with a ledger row. Its result counts both lists (`counts`) and names the chapters `notReady`: a reviewer that could not close a finding lists it under `open`.
4. **`node scripts/batch-finish.mjs <book> <the review run's journal.jsonl> <question prefix>`** does the steps after the run in one command and prints only what needs a person. The journal's path is in the Workflow result (“Transcript dir”). It runs:
   - **`scripts/batch-notes.mjs <book> <journal>`**, which appends the reader questions no source answered to `content/<book>/UNANSWERED.md`, saves the reviewers' theme leads to `.cache/batch/<book>/theme-leads.md` (working notes, not filed), and prints anything a reviewer left for the author, for the coordinator to settle (`AUTHORING.md`, “Decide, don't defer”).
   - **`scripts/merge-sources.mjs <book> <chapters… | page file name> [--write]`**, which gathers the proposed entries and reports what has to be settled by hand (a key already used for another page, one key proposed for two pages, one page under two keys); `--write` appends the rest to `content/sources.yaml`.
   - **`scripts/batch-commit.mjs <book> reviewed <chapters…>`** for the ready chapters, which runs `check-chapter.mjs` and commits one chapter at a time with its ledger and the record of its prose review (“What is recorded,” below); a chapter that is not ready is committed with `written`, without that record.
   - **`scripts/codex-themes.mjs <book> [--model] [--force] [--print]`** when the batch has written the book's last chapter: Codex's read-only review of the theme candidates, written to `.cache/batch/<book>/reports/themes-codex.md` (skipped if that exists).
5. **A chapter left not ready** gets a focused writer repair for its open items (an Opus `chapter-writer`, the Sonnet check, then `review-chapters` on that chapter with `across` set to its batch), and is committed with `batch-commit.mjs <book> reviewed <n>`.
6. **`node scripts/check-content.mjs <book> --repeats`** over the batch, to see passages several chapters quote from the same source, which one explanation and a link may replace. A Church teaching manual cited in a new chapter is a fault to repair before the batch is committed (`STANDARDS.md` §1).
7. **With the last batch** (`lastBatch: true`), `review-chapters` ends by running `create-book-art` if every reviewer reported its chapter ready (otherwise its result's `next` says which chapters hold it up, and the coordinator runs `create-book-art` by name after the repairs), then `.claude/workflows/propose-themes.js` (`args`: `book`, `leads`, `model`), in which one Fable agent reads the finished book and writes `.cache/batch/<book>/reports/themes-fable.md`. What the coordinator does with the two theme lists is in `AUTHORING.md` (“Theme candidates at the end of a book”); the image is “Book illustration workflow” below. The build warns about a finished book whose `visual.yaml` is missing or not approved, so the stage can't be forgotten.

**What to expect of a batch** (Nehemiah, 2026-11-17; `DECISIONS.md`, “Codex reads before the reviewer”): a median of about 11 checker findings a chapter with nearly nine in ten acted on, about 10 Codex findings with nine in ten acted on, and every chapter ready. A batch whose reviewers act on clearly fewer, or leave several chapters not ready, is worth a look before the next: compare the review run's `counts`, and `node scripts/batch-usage.cjs <the runs' transcript folders>`, with these. Until 2026-11-17 the reviewer came first and `codex-pass` applied Codex's findings in a separate stage; that arrangement is at commit `584c7225`, and `codex-pass` remains the pass for a finished chapter that changes later.

**Theme pages and guides** (`PAGES.md` has the steps and who writes what):

- **`scripts/theme-dossier.mjs <book> <dossier path> --words "w1,w2" [--stem] [--hebrew H1,H2] [--verses "c:v,…"] [--site all]`** starts a dossier with what a script fills exactly: every occurrence of the words (and of each Hebrew word) in the text, the same phrases in every other book, the Church's heading, footnotes and *Scripture Helps* for each key verse's chapter, and what the site already says, each under the command that made it. For a volume's guide (`theme-dossier.mjs old-testament <dossier> --words "…" --verses "genesis 16:13,exodus 21:10"`) the words are searched in every book and on the whole site, and each key verse names its book. The `theme-researcher` fills the rest.
- **`.claude/workflows/write-theme.js`** (`args`: `book`, `file`, `dossier`, `outline`, `writerModel`, `codexModel`) writes a shorter theme page: an Opus `theme-writer` writes the page, its ledger and its proposed sources from the session's outline and the dossier; an Opus `theme-reviewer` returns a verdict and required fixes; the writer makes them; then an Opus agent runs `codex-read.mjs` on the page and applies the findings that hold up, adding nothing. Each runs `check-page.mjs`. Afterwards the coordinator runs `merge-sources.mjs <book> <file> --write`, commits the page with its ledger, and shows it in the preview. An essay and a guide do not go through it: the coordinating session writes them itself and spawns one `theme-reviewer`.
- **`scripts/link-theme.mjs <book> <chapter> <verse> "<note title>" "<sentence>"`** appends the one sentence that links a chapter note to a theme page, without reformatting the file; it changes nothing if the note is already linked. Give every quotation in the sentence its `[[reference]]`. A linked chapter's prose review is no longer current, so it gets a pass of its own (“The second reader,” below).

**Keeping track:**

- **`scripts/status.mjs [book]`** prints where each book stands, from the files themselves: chapters written (a chapter with no `setting` is bare), ledgers, theme, guide and facsimile pages (with those unread or in the old form), `status: preview`, `visual.yaml`'s status, each volume's guides, the question numbers under the book's heading in `OPEN-QUESTIONS.md`, commits not on `origin/main`, and the chapters whose language pass a commit's trailers record. No document repeats any of this.
- **`scripts/batch-usage.cjs <a Workflow run's transcript folder> [--calls]`** reports what a batch cost, from the agents' transcripts: for each role and model, a chapter's average steps, tool calls and tokens; `--calls` adds which commands each role ran and how much each returned. It is how one arrangement is compared with the last, and it shows which model each role actually ran on.
- **`scripts/progress-page.mjs <book> [--writing 94-105] [--pass 85,88-93] [--note "…"]`** writes `.cache/progress/<book>.html` for a long run; publish it as an artifact after each batch (2026-10-11).
- **`scripts/review-dashboard.mjs [outDir]`** exports one row per theme page and guide that carries `review:` in its front matter as `review-tasks.json`, and the commits since 2026-10-25 that rewrote or deleted a theme page as `review-commits.json` (default `.cache/batch/dashboard`), for the author's claude.ai dashboard “Theme page review”; a session then uploads the two files as the artifact's blobs and points its `datasets/tasks` and `datasets/commits` documents at them.

**Lessons for the coordinator** (each learned once; the incidents are in git):

- Don't change the session's working directory while a batch runs: agents started afterwards work in the other copy.
- A new worktree has no `node_modules`, and the build then fails on a font file: link the main checkout's (`ln -s <main checkout>/node_modules node_modules`, which git ignores) before the first batch.
- When one Codex reading hangs and is killed, run the batch again without `--force`: it skips the readings that are current.
- `codex-pass` on one chapter, without `across`, names a side-by-side reading that does not exist, and the applier reports it under `problems`, so the chapter comes back not ready. If that is the only problem, `needsWriter` is empty and `check-pass.mjs` is clean, record the pass.
- Don't `git commit -a` while a batch runs; name the files. In zsh a variable holding a list of chapters is one argument; write the numbers out.
- A workflow run by name from a worktree runs the main checkout's copy of the script. Run a workflow changed on the branch with `scriptPath` until it reaches `main`.
- A message the author sends while a batch runs is shown to every agent that starts afterwards as its request; most answer it in their report, some stop. After such a batch, look for a chapter with no file, a reviewer's question addressed to the coordinator, and a chapter a review or pass left unchanged, and run those again. For the same reason, start a review or a pass when the author's last word was about the chapters.
- An agent that refuses to write its report, taking an instruction against writing documents to forbid it: save its final message as the file.
- A reviewer that pulls an earlier version of a chapter out of git has reviewed the wrong text: redo the review.
- `check-ledger` passes a Hebrew row whose quoted word is on the page but is the wrong word for its claim, so a reviewer still reads the Hebrew rows against their claims.
- When `check-ledger` suddenly fails several Hebrew rows, or `hebrew.mjs` says a chapter has no verses, a cached page is cut off: delete that URL's file in `.cache/ledger/` and run the check again.
- When a workflow stage shows no file change for ten minutes, look for a `cat`, `sleep` or `pgrep` loop under the agent's shell and kill it; the agent carries on.
- Ask for a theme dossier under about 400 lines, script output summarized. A researcher that hands in its dossier saying it still has work running may go on changing it: wait for its final notice, or reread the dossier's end, before starting the writer.

## The second reader

Every new page is read by Codex, a model of another family, before the author sees it (`STANDARDS.md` §11). It is read-only, opens no source and judges no citation: it checks answer, progression, integration and language under `STANDARDS.md` §2–3, and may say that reasoning is missing, not supply it.

**Codex's readings, from the shell:** `node scripts/codex-read.mjs <book> <from>-<to> --batch` (the `codex` CLI signed in: `codex login status`). It reads the batch side by side (`reports/NN-NN-codex.md`), then each chapter alone with its text in the prompt (`--inline`; `reports/NN-codex.md`). A `.meta.json` beside each report fingerprints the chapter's text, the reader, its criteria and the model, so only a current reading is skipped; `--force` rereads anyway and `--print` shows the prompt without a model call. Codex's limit is the ChatGPT plan's, not Claude's: about 70 readings a window, more with a smaller model (`--model`). A reading that hangs is killed and the batch run again; it skips what is done.

**What is recorded.** A chapter's completed prose review is a commit whose trailers carry `Prose-Review: 1`, `Reviewed-Chapter` and a `Reviewed-Source` hash of the chapter (`scripts/prose-review.mjs` supplies the version, the hash and the parser that `batch-commit.mjs` and `status.mjs` share, and reads the commits without a path filter). `batch-commit.mjs` writes them, with `reviewed` for a new chapter and `pass` for a later pass, so `node scripts/status.mjs <book>` shows what is waiting, and a chapter changed since its review is marked not current. A language-pass commit from before 2026-10-28 does not certify a chapter under the prose criteria of `STANDARDS.md` §3. No other list is kept.

**A finished chapter that changes later** (a note deepened from the author's study, a sentence linking it to a theme page) gets a pass of its own, which adds nothing:

1. `node scripts/codex-read.mjs <book> <n> --inline` for each changed chapter (and `<from>-<to> --across` when a whole batch changed).
2. The `codex-pass` workflow (`.claude/workflows/codex-pass.js`; `args`: `book`, `chapters`, `across`, `codexModel`, `applyModel`): one Opus agent per chapter decides the findings, applies the repairs that preserve existing meaning, and reruns `check-chapter`. A real gap that needs added reasoning, an interpretation or a connection goes in `needsWriter`, not in `declined`. The workflow returns `readyChapters` (no outstanding writer work, missing result or failed check) and `notReady`.
3. Resolve each `needsWriter` item with a focused writer repair, the source check and the review, committed separately; then reread and apply again. The gap is not permission to invent the missing connection.
4. `node scripts/check-pass.mjs <book> <chapters…>` sets the pass's edits beside the last commit and fails on an added ledger row. A new reference should only be a pointer to another chapter's note, and a “new or changed quotation” is usually an old one whose closing punctuation moved. Read its ledger counts: an applier may not cut a sourced sentence and delete its row on a `[prose]` finding; put the sentence back.
5. Read `declined` and `problems`. Settle taste by the standard; only a genuine choice of doctrine or of the author's wording goes to `OPEN-QUESTIONS.md`.
6. Record only `readyChapters`, with `node scripts/batch-commit.mjs <book> pass <chapters…>`, which commits even when no edit was needed. The pass touches only the assigned chapters and ledgers.

**Other pages** (a theme or guide page, a book page, a facsimile page, the About page) are read one at a time: `node scripts/codex-read.mjs <book> <page file name>`, `<book> book`, `<book> facsimile-<n>`, or `--file <path>` (reports to `.cache/codex/`); `<book>` may be a volume. Apply supported language findings without adding claims. A substantive gap goes back to that page's writer and its source and review checks before a fresh reading. Rerun the page's checks (`check-page.mjs` for a theme or guide page; the build for a book page).

**The chapter-note check of 2026-10-27** (Codex read every chapter's notes, calibrated and adjudicated) is complete: the annotated tag `chapter-prose-review-2026-10-28` holds the reviewed versions and the 33 notes and two threads it diagnosed, all of them in the Old Testament; they were repaired on 2026-11-18 (writer repair, source check, review, then Codex's reading and the language pass). No further corpus-wide campaign runs unless the author asks.

## Book illustration workflow

Every completed book gets one full-width landing-page illustration, unless the author has said it needs none: then `art: none` in its `book.yaml`, with `artWhy:`, stops the build's warning (the Articles of Faith, 2026-11-17: statements of belief, not a story or a place). This is an **AI authoring stage**, after all its chapters have passed review, and never part of the site build. The coordinator runs `.claude/workflows/create-book-art.js` (`write-chapters` runs it at the end of a book's last batch, when called with `lastBatch: true`). It has two steps:

1. **Direct.** `book-art-director` reads the finished book and saves its summary, motifs, composition, and proposed alt text in `content/<book>/visual.yaml` with `status: proposed`.
2. **Generate.** `node scripts/book-art.mjs generate <book>` builds the prompt from `content/visual-style.yaml` (the permanent visual identity) and that brief, and runs `codex exec`, whose built-in image tool draws one candidate. The script copies it from Codex's own folder (`~/.codex/generated_images/`) to `.cache/book-art/<book>/candidate-N.png`, which is not committed. Codex is run read-only and writes nothing in the repository. It needs the `codex` CLI signed in (`codex login status`), no API key. That tool takes no pixel size: at 16:9 it returns 1672×941, the size of every book image on the site, which the author accepts. If Codex answers that its model is at capacity, run it again or pass `--model <another Codex model>` (`codexModel` in the workflow's `args`). `node scripts/book-art.mjs prompt <book>` prints the prompt without drawing anything. Run `generate` again for another candidate, after editing the brief if the idea should change. `generate` redraws the whole scene, so when the author likes a candidate but for one thing, `node scripts/book-art.mjs edit <book> --from <candidate.png> --change "<the one change>"` gives Codex that candidate as its input and asks for only that change (author, 2026-10-23, after a request to shrink Zechariah's lampstand redrew everything: “Just shrinking the lamp and keeping everything else the same would have been perfect”); it saves the next `candidate-N.png`. The site’s style rule allows no people; a brief may carry `figures:`, one sentence saying which small figures the author has allowed for that book, and it then replaces that rule in the prompt (first used for Moses, 2026-10-06: Adam and Eve, tiny and seen from behind). A brief may also carry `look:`, one paragraph naming the medium for that book alone; it replaces the site's style in the prompt and leaves out the site's rules that require a drawn, poster-like image (first used for Exodus, 2026-10-12, when the author found the house style “too cartoonish” and said he might be “shifting more toward photo-realism”; `content/visual-style.yaml` itself is unchanged until the author says so).

The author reviews the candidate. Only after approval does the coordinator run `node scripts/book-art.mjs approve <book>` (the newest candidate, or `--from <file>`; `--force` to replace an existing image), which saves it as a JPEG at `src/assets/<book>-book-art.jpg` (a tenth of the PNG’s size, made with `sips` on a Mac or ImageMagick elsewhere) and sets `asset` and `status: approved` in the brief. Then trim the brief's `motifs`, `composition`, and `alt` to describe the image that was kept (ideas tried and dropped along the way don't stay in an approved brief), and build the site. Then write the brief's `key`, “What's in this picture” (author, 2026-10-13: “One thing I really struggle with is seeing symbols in someone else's artwork. I don't want someone to struggle with that”): one line for each thing that is actually in the approved image, in plain words, saying which verse it shows, with the verse quoted exactly and its `[[reference]]`; a bold opening names the thing as the reader sees it. Look at the image itself, not only the brief, since an image can leave a motif out or add one. Check every quotation against `data/kjv/<book>.json`, have Codex read the list (`codex-read.mjs --file`), and build. The book page shows it under the image, behind a faint eye icon in the image's lower right corner (`artFigure` in `src/templates/pages.mjs`, `.art-key` in `site.css`, and a few lines in `site.js` that keep the icon on the image while the list is open). The renderer reads approved briefs automatically, so a new book never needs a book-specific template edit. Until a finished book has an approved brief whose asset exists, the build warns and the book page keeps the placeholder art. A volume’s picture is made the same way by hand, since `book-art.mjs` takes only books: a brief in `content/volumes/<volume>/visual.yaml`, Codex drawing from a prompt written for it, the approved PNG saved as `src/assets/<volume>-volume-art.jpg` with `sips`, and its key written and checked as above (`DEVELOPMENT.md`, “Volume pages”). A volume’s picture may leave the house style: the Old Testament’s is a newly made mosaic, not worn, so it does not pass for a copy of a real ancient floor (author, 2026-11-17).

**What the image tool has taught** (from the author's rulings and the images the author approved, 2026-10-06 to 11-13; the incidents are in git). A line marked *(a lesson)* is the coordinator's reading of an approved image, not something the author said:

- **Each object must remind the reader of a message the chapters teach, not only of an event** (2026-11-05). Test every motif by what a reader who knows the chapters would be reminded of; an object whose message needs the key to be found at all is the wrong object.
- **An object the Bible describes is asked for in the Bible's own words**, with “draw it as you understand that description,” not in poses of the drafter's.
- **An object is asked for by the shape that makes it that object** (a sling as a limp, flat scrap of leather that takes a shape only with a stone in it; a coat of armor by its buckled shoulder straps), and checked after every edit: each edit redraws the foreground, so count what the verse counts.
- **A state the tool can't draw is asked for by what shows it, not by its name** (a ram “caught in a thicket” by its braced legs, its weight thrown back, its horns buried in the bush). Keep an animal small and in the middle distance; a large one poses.
- **A candidate the author likes but for one thing is edited, not redrawn** (`book-art.mjs edit`): `generate` changes the whole scene.
- **After about five failed tries, take the object out**: change the picture, not the description. When a detailed brief keeps missing, try a generic prompt that leaves the subject to Codex.
- **Water is drawn running sideways across the picture**, from its source to where it goes; the tool won't draw it running away from the viewer. A spring is water out of a crack with no pool.
- **A scene that looks too regular** (rows, a patchwork, even bends) is fixed by asking for fewer and larger things, not for irregularity.
- **Say where the light comes from and which way the shadows fall**, and refuse a candidate with light nothing in it could cast; several natural lights (moon and stars) are fine.
- *(a lesson)* **A book with many stories may do well with a few places and open ground between them**, not one for each story: Genesis's approved image (2026-10-12) follows a river through three places, after a tower for Babel was tried and taken out as too prominent.
- **Draw one book at a time.** `book-art.mjs generate` takes the newest image in Codex's folder, so two run at once can both save the same picture (2026-11-17); look at each candidate before showing it.
- **Objects are of the book's time.** The author may allow a figure though the house style says none (`figures:`). Never ask for a look “halfway between” two candidates, since the tool swings past both: name one concrete look, or keep the one the author liked.

## Reviewing the instructions

The instruction files (`CLAUDE.md`, `AUTHORING.md`, `STANDARDS.md`, `PAGES.md`, `PROCESS.md`, `DEVELOPMENT.md`, the agent and workflow files) grow a line at a time, and what was true when a line was written stops being true. A review on the most capable model is worth its cost now and then, and not on a calendar: `node scripts/status.mjs` ends with how many commits have touched these files since the last review, how much they have grown, and how many chapters have been written since, and says when a review is due (40 commits, a quarter in size, or 50 chapters). After a review, tag it: `git tag review-YYYY-MM-DD`.

The review's checklist, so that it starts from the same questions each time (first run 2026-10-11, on Fable; it found a dead script reference, a script whose purpose had ended, a README three books out of date, the scripts documented in four places, and the standard being read whole by agents that needed half of it):

1. `node scripts/check-docs.mjs` first: stale references are mechanical.
2. For each document, what it says that is no longer true: a file, section, environment or step that no longer exists; a “not yet” that has since been done; a rule for a situation that no longer arises.
3. What is said in more than one place (a script's options, a process's steps, a rule restated in an agent file), and which one place should hold it.
4. What each agent reads before working, in kilobytes, against what its role needs.
5. What an agent does by hand that a script could do exactly (`AUTHORING.md`, “Offload to scripts what a script can do exactly”), from the last batch's `batch-usage.cjs --calls` output.
6. Incidents recorded as stories where a one-line rule would do, and an author's quotation where the date would do (the second run, 2026-11-17, on Fable, cut `AUTHORING.md` by two thirds this way).
7. What the last weeks' transcripts say each step cost and caught (`batch-usage.cjs`; the reviewers' and appliers' results are in each run's `journal.jsonl`), before any step is added or removed.
