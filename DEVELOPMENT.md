# Development notes

How the site's code works: read this before changing the build, templates, styles, or scripts, or when adding a book. For building and previewing, see `README.md`.

## Hosting

The site is served at https://scriptures.conlin.io by Cloudflare, which rebuilds it from this repository whenever `main` is pushed; there is no GitHub deploy workflow. `npm run build` writes a plain static site to `dist/`. `wrangler.jsonc` tells Cloudflare to serve `dist/` and to answer missing paths with `404.html`, which redirects `/Isaiah`, `/isa/53`, and similar paths to their canonical URLs. Its `name` must match the Worker's name in Cloudflare. The repo is at `git@github.com:jlconlin/Scriptures.git`.

**The dev site** (author, 2026-10-16) is https://scriptures-dev.conlin.io: a second Cloudflare Worker, `scriptures-dev`, built from the same repository with `dev` as its production branch (deploy command `npx wrangler deploy --name scriptures-dev`, since `wrangler.jsonc` names the live Worker). Work is pushed to `dev` when the author asks to see it there, on a real device (`AUTHORING.md`, “Showing a change”); otherwise a change is shown in the local preview, and once approved `main` is fast-forwarded and the live site follows. Cloudflare sets `WORKERS_CI_BRANCH` in a build, and a build from any branch but `main` marks every page `noindex` and writes a `robots.txt` that disallows all (`SITE.noindex` in `src/site.mjs`), so only the live site is listed by search engines. The dev site's offline copy and Home Screen icon are separate from the live site's.

## Checks

What each script does. `scripts/dev.mjs` (`npm run dev`) is the local preview: it builds the site with the books in preview, serves `dist/` on port 4321, and rebuilds when content or source changes. It serves the checkout its own file is in, and `.claude/launch.json` starts the main checkout's; to look at a worktree, run that worktree's `scripts/dev.mjs` on another port (`PORT=4324`). `STANDARDS.md` §9–10 says when to use them; the commands are listed there. Shared code: `src/lib/pages.mjs` (fetching, the page cache, comparing a quote with a page, `pageProblems`, `parseOrEmpty`), `src/lib/ledger.mjs` (proposed sources, a row's `where`, wiki hosts, a theme page's sections) and `src/lib/hebrew.mjs`. None of the checks is part of `npm run build`, so an unaudited chapter can't break the Cloudflare build.

### The checks

- **`scripts/check-content.mjs`** (`npm run check`) checks sourcing and writing. A second argument that is not a number is a page's file name (`node scripts/check-content.mjs jeremiah cup-of-fury`): only that page is checked.
  - *Errors, everywhere:* an unknown source key; a wiki URL.
  - *Errors, in a chapter with a ledger:* a note with no sources; a cited key with no quoted ledger row; a pointer to a note that isn't there (“see the note on [[Gen. 11:3]]”, “the note on verse 5”). The reference is resolved with the table in `src/lib/refs.mjs`; a book not on the site is skipped; the Church edition's own footnote (“the Church edition's note on verse 24”) is not a pointer. In a chapter without a ledger a bad pointer is a warning.
  - *Warnings about the Student Manuals* (`STANDARDS.md` §1), never errors: more than a third of the notes citing one, or a note citing one with no source from beyond the Church's own publications beside it. “Church's own” is decided by the host of the source's URL in `sources.yaml` (`CHURCH_HOSTS`); a source is a Student Manual when its `pub` says “Student Manual”.
  - *Other warnings, each under its own heading:* a chapter well past the length guideline; a source announced in a note, `setting`, `thread`, `christ`, or `explore` (“the manual says”, “one commentator notes”; the subjects and verbs are `ANNOUNCERS` and `ANNOUNCE_VERBS`); a modern scholar named in running text (the surnames of the authors of articles, books and web pages in `sources.yaml`, leaving out ancient writers, ordinary-word surnames and anyone the Church publishes or who gave a talk, `ANCIENT`, `COMMON`, `CHURCH_AUTHORS`; a name with “Elder” or “President” in the same sentence is allowed); a `[@key]` marker in a chapter file; a note whose first sentence withholds its subject (“This note is about…”, “This is the hardest…”); more than a third of a chapter's notes citing a commentary read on Bible Hub (a URL under `biblehub.com/commentaries/`); a `setting` under 120 or over 280 words; a theme page titled as a chapter of its book is.
  - *Per-note coverage of the ledger* (warnings): a note with no ledger row whose `where` names it; a key in a note's `sources` with no row for that note (not repeated for a note with no row at all, and not `lds-scriptures`); a `where` that names no note or section (`partsOfWhere` compares note titles on letters, so straight and curly quotes agree; a retitled note is reported once, naming the closest title, and its rows then count for that note); and a passage of 12 or more characters in curly quotes in a note's body that no row for that note quotes, that is not followed in its sentence by a `[[reference]]` (`check-quotes` has those), and that is not a phrase of the chapter's own verses.
  - *A volume's guides* (`content/volumes/<volume>/guides/`) are checked as a book's are: `node scripts/check-content.mjs old-testament` or `old-testament <page file name>`.
  - *Guide and theme pages:* a theme page over 1,000 words (`PAGE_WORDS`; a guide is not held to it); a source announced in the text, by section; a `[@key]` cited in a section whose ledger has no row for that key under that section (a row's `where` is read as `opening` or `section “Heading”` and compared with the page's headings, `## …` or `<h2>`, letters only). It lists, as information, every ledger row whose claim begins “Connection made by this page:”.
  - *Proposed sources:* when one chapter is checked and `.cache/batch/<book>/proposed/NN.yaml` exists (or one page, and `proposed/<page file name>.yaml`), its entries are added to `sources.yaml` in memory and the keys that came from there are printed (`--proposed` does it for every file of a book, `--no-proposed` not at all; `--root` still works). A proposed key that gives another URL than `sources.yaml`'s is an error; one that nothing in the chapter cites is a warning.
  - `--repeats` lists passages of 12 or more words that the ledgers of three or more chapters of a book quote from the same source (not scripture, lexicons, or dictionary entries, which `REFERENCE_KEY` and the `entry` type leave out), so the coordinator can see what should be explained once and linked.
- **`scripts/check-ledger.mjs <book or volume> [n... | themes | guides | facsimiles | <page file name>]`** reopens every ledger row's URL and confirms the quote is on the page, comparing letters only (footnote markers, verse numbers and Strong's annotations get in the way otherwise). With nothing after the book it takes every chapter, then the theme and guide ledgers. It reads a web page as a reader sees it, the footnotes the Gospel Library keeps in the page's embedded data, a raw text or XML file as it is, and a PDF with a text layer; a quote with hardly any letters (a footnote's cross-reference) is compared with its digits kept. Pages are cached in `.cache/ledger/` for a day (`--fresh` refetches), and the research scripts share the cache, so a page fetched by anyone today is fetched once. A Scripture Central KnoWhy is read from its API (the public page needs a browser) and kept under the public URL; a PDF is kept as its text with a page break between pages. **It proves quotes are real, not that they support their claims.**
- **`scripts/check-chapter.mjs <book> <chapter>`** runs `fix-yaml`, the build (`PREVIEW=1 BUILD_OUT=.cache/batch/<book>/dist-NN`), `check-quotes`, `check-content` (with the proposed entries) and `check-ledger`, prints a one-line result for each and, under it, only the lines that concern the chapter, and exits 1 if one fails (`--skip` leaves checks out).
- **`scripts/check-page.mjs <book or volume> <page file name>`** is `check-chapter` for a guide or theme page: the build (into `.cache/batch/<owner>/dist-<page>`), `check-quotes`, `check-content` and `check-ledger` for that page, and `check-sources` on its proposed entries when `.cache/batch/<owner>/proposed/<page file name>.yaml` exists; one line a check, the page's word count, and only the lines that concern the page. `check-quotes <book or volume> <page file name>` checks one page's scripture quotations by itself.
- **`scripts/check-sources.mjs <book> <chapters…>`** (or `<book or volume> <page file name>`, or `--keys a,b`, or `--all`) is `STANDARDS.md` §4 rule 10: it opens each proposed entry's URL and sets the entry's title, author and `pub` beside the page's title and first heading. It flags a page that did not load or is a block, not-found or almost-empty page; a Bible Dictionary, Guide to the Scriptures or Topical Guide URL whose heading is not the entry's title (a missing entry still returns a page); a wiki host; a PDF with no text layer; and a title that shares no significant word with the page's. It exits 1 if anything is flagged. A few entries are always flagged because their sites answer a script with a challenge page or a title unlike the entry's (ScholarsArchive, Sefaria, a DOI link, some Joseph Smith Papers transcripts, archive.org items).
- **`scripts/check-docs.mjs`** (first in `npm run check`) checks the project's own documents against the repository: every `scripts/<name>` a document names exists, every `STANDARDS.md` §n cited exists, every quoted path exists, every script is named in some document, `AGENTS.md` is a copy of `CLAUDE.md`, and `package.json`'s scripts exist. It also prints how far the instruction files have drifted since the last review tag (“Reviewing the instructions,” below); `status.mjs` prints the same line.
- **`scripts/check-kjv.mjs <book>`** compares `data/kjv/<book>.json` verse by verse with the Gospel Library edition, including where LORD and GOD are in small capitals.
- **`scripts/test-source.mjs`** checks that what `source.mjs` prints is found by `check-ledger`'s own comparison, for each kind of page (`--sweep` tries every 20 words of every page). It fetches real pages, so it is not part of `npm run check`.

### Research scripts

They do the mechanical reading for the agents, and a page they print is verbatim, so a ledger quote can be copied from it.

When the connection is unavailable, `source.mjs` and `check-ledger.mjs` accept **`--offline`**, which reads saved snapshots regardless of age and never fetches or refreshes them. Add `--cache-dir <path>` to read another checkout's `.cache/ledger` without writing there. The reader prints the snapshot's saved time; the checker labels its result offline. These checks establish what the saved page says, not whether the page is currently reachable. Neither option can be combined with `--fresh`, and `--cache-dir` requires `--offline`.

- **`scripts/source.mjs <url>`** prints a page's own text: by itself a title, a size, and an outline (headings with the paragraph numbers under each); `--find "words"` the paragraphs that contain all the words (a window around the match for a long paragraph, such as a PDF page; it may be given more than once, and searches headings too); `--para 12-20`; `--all`; `--notes` (footnotes or endnotes with their markers and links).
  - It reads the Gospel Library (the embedded data: scripture chapters, Bible Dictionary, manuals, talks, with their footnotes), KnoWhys, Joseph Smith Papers transcripts (without the pop-ups), PDFs (one paragraph per page), and any other HTML page or text file (the main content of Bible Hub, rsc.byu.edu, byustudies.byu.edu; archive.org's `_djvu.txt`).
  - Paragraphs of a Gospel Library page keep the Church's own numbers (the id in a link), **except on a scripture chapter**, where they are numbered by verse and printed “v. 36”: the Church's paragraph ids count the headnote, subtitle and chapter heading too, so they run ahead of the verses. `--para 36-39` (or `--verse`) takes verse numbers there, and the headnote, chapter heading and subtitle are paragraphs of their own, labelled (`--para headnote`).
  - A manual's contents page is read as the list of its chapters with their addresses, and a Gospel Library table as one paragraph per row, its cells separated by “ | ”.
  - **`--append <dossier> --key <key> [--claim "…"] [--under "4"]`**, with `--para` or `--find`, writes the paragraphs into a research dossier as rows (claim, key, URL, where on the page, then the text verbatim) under the section named, and prints one line. A researcher reads a page once and never types a quote (the row cost its tokens twice before: once read, once written).
  - A page that is the site's own not-found page, a block or challenge page, a PDF with no text layer, or a page with no readable text is said to be that on standard error, with exit 1 (`pageProblems`); `check-ledger` and `ledger-context` report such a page as that, not as “quote not on page”. If a page reads badly, `curl` is the fallback (`STANDARDS.md` §9).
- **`scripts/footnotes.mjs <book> <chapter>`** prints the Church's chapter heading, every footnote by verse (Joseph Smith Translation readings marked), and the *Scripture Helps* chapter that covers the chapter (found from the manual's contents page, Old and New Testament), with its sections and every endnote and its link, or says there is none. By default only the sections and endnotes that bear on the chapter are printed: those with a verse range in it, and (marked ◆) those with no verse range, which belong to the whole of the manual's chapter; `--all-notes` prints every one.
  - **`--compare`** is the checker's comparison with the Gospel Library (“don't replicate it”, `STANDARDS.md` §1): for each note of the written chapter, the Church's footnotes on its verses beside the note's own `[[references]]`, with which are already in them; and for each *Scripture Helps* section on those verses, its heading and text (once) and each endnote with every non-scripture link: whether the page is readable and whether a ledger row of the chapter cites that URL. Whether a note says more than the footnote stays the agent's judgment.
- **`scripts/hebrew.mjs <book> <chapter>:<verse>[-<verse>]`** prints each word of a verse in the Westminster Leningrad Codex (the Open Scriptures Hebrew Bible, `wlc/<Book>.xml`) with its Strong's number, morphology code, and lexicon page; `<book> --word <strongs>` prints every verse in the book where a word occurs, with the count. References are the King James Version's, which the site uses, and the Hebrew's is printed beside one that differs (“Mal 4:5 (Hebrew 3:23)”; `--wlc` takes Hebrew numbers). The mapping is the Open Scriptures verse map (`wlc/VerseMap.xml` in `openscriptures/morphhb`), which covers the chapters that divide differently in 27 books and the Psalm titles. A King James verse the Hebrew file lacks gets a warning that names the Hebrew chapter it falls in; a half-verse is marked as part of the verse.
- **`scripts/occurrences.mjs <book> "<words>"`** is where a theme page starts (`STANDARDS.md` §8): every verse of `data/kjv/<book>.json` that has the phrase (case-insensitive, whole words; several phrases say which each verse matched), with a count by chapter and in all.
  - `--stem` matches a word and its regular endings (*remembered* finds *remember*, *remembereth*; the endings are `ENDINGS` and `TAKE_OFF`; an irregular form such as *begat* is a phrase of its own).
  - `--books` (or the book `all`) searches every book in `data/kjv/`.
  - `--hebrew <strongs>` lists every verse where that word occurs in the Hebrew, with the King James verse beside it.
  - `--site [all]` lists every note, chapter `setting`, `thread`, `christ` and `explore`, and theme and guide page section in `content/<book>/` (every book, and every volume's guides, with `all`; a volume's alone with `old-testament`) that has the phrase, as book, chapter, verse, note title, and the sentence that has it.
- **`scripts/ledger-context.mjs <book or volume> <chapter | page file name>`** is the checker's reading of a ledger: grouped by each row's `where`, in the chapter's order, the text of that part (a note's title, phrase and body; `setting`; a theme page's section), then each row's claim, key and URL and the paragraph of its page that holds the quote with the paragraph before and after, the quote marked ⟦like this⟧ (found with `check-ledger`'s own comparison, `quoteParts`; a Gospel Library footnote counts as a paragraph, shown with its verse; a long paragraph is cut to a window), or “quote not found” or “page not fetched”. `--keys`, `--skip-keys`, `--where` and `--types` (the source's `type` in `sources.yaml`: article, book, entry, hymn, manual, talk, web) choose the rows; a proposed source not yet in `sources.yaml` is read from the proposed file.
- **`scripts/knowhys.mjs "<words>"`** or **`<book> <chapter>`** searches Scripture Central's KnoWhys by title, main reference, summary and body (the whole listing from the API, kept in `.cache/knowhys/list.json` for a day) and prints number, title, date, main reference, public URL and the sentence around the match; by chapter, those whose main reference is in the chapter come first, then those that name it.
- **`scripts/search-lds.mjs "<words>"`** is one search across the Latter-day Saint study sites a brief starts from (`AUTHORING.md`, “A book's first research”), each the way it answers a script (tested 2026-10-13): the Religious Studies Center through its own full-text search (`rsc.byu.edu/search/<words>`), with the passage around the match and a chapter's several printings folded into one line; BYU Studies and the *Interpreter* journal through their sitemaps, which finds an article only when every word is in its address, so in its title; Scripture Central's KnoWhys through `knowhys.mjs`. Scripture Central's library of articles and book chapters answers only a browser (its search service and content API refuse a script, and `archive.bookofmormoncentral.org` returned an error), so the script says what it did not search and prints the web search limited to that site to make instead. `--site rsc,byustudies,interpreter,sc` chooses, `--max N`, `--fresh`.
- **`scripts/pdf-text.mjs`** prints a PDF's text (pdfjs-dist).

## Writing a book in batches

The steps a coordinating session repeats for every batch of chapters are scripts in the repository, so they are not rebuilt each time.

- **`.claude/workflows/write-chapters.js`**: the Workflow script. `args`: `book`, `chapters` (about twelve at a time), `writerModel` (`opus` by default, or `sonnet`), `models` (finished chapters of the book to imitate), `focus` (the author's questions, by chapter number), `lastBatch` (`true` when these chapters finish the book; see the last step below), `themes` (`false` for a book the author has said needs no theme pages: no `propose-themes`, and run `batch-finish.mjs` with `--no-themes`). Each chapter goes to a `chapter-writer` (Opus), then to a `chapter-checker` (Sonnet), which reopens the sources and writes its findings, then to a `chapter-reviewer` (Opus), which decides them and repairs the chapter (`STANDARDS.md` §11). Run it by name, or with `scriptPath`; if the usage limit or a restart stops it, run it again with `resumeFromRunId` and the same `args`, and finished agents are not repeated. The agents leave working files in `.cache/batch/<book>/` (not committed): `proposed/NN.yaml`, the `sources.yaml` entries a chapter needs, `reports/NN-writer.md`, and the checker's findings, `reports/NN-check.md`.
- **`.claude/workflows/codex-pass.js`** (`args`: `book`, `chapters`, `codexModel`): the language pass, run on a batch after its chapters are committed. **`scripts/codex-read.mjs <book> <chapter>`** has Codex read one finished chapter against `STANDARDS.md` §2–3 and write numbered findings to `.cache/batch/<book>/reports/NN-codex.md`; with `<from>-<to> --across` it reads the chapters side by side for what repeats or disagrees between them (`NN-NN-codex.md`); **`<from>-<to> --batch`** does both for a whole batch from the shell, skipping a findings file that exists, and is run before the workflow, which no longer runs Codex itself (an agent spawned only to run a command was a waste; 2026-10-11). Other pages: `<book> book` reads the book page’s own words in `book.yaml` and checks its quoted verses against the text (`reports/book-codex.md`); `<book> <page file name>` a theme, guide or facsimile page; `--file <path>` any other page, such as `content/about.md` or a volume introduction (`.cache/codex/<name>-codex.md`). Codex runs read-only (`codex exec --sandbox read-only`), opens no source, and is told never to suggest an addition; `--print` shows the prompt. The workflow then runs one Opus agent per chapter, which decides the findings, edits only that chapter’s two files, adds nothing, and reruns `check-chapter`. **`scripts/check-pass.mjs <book> <chapters…>`** then sets each edited chapter beside its last commit and lists what the pass added (new `[[references]]`, new or changed quotations, ledger rows, the change in words; exit 1 if a row was added). Commit each chapter again afterwards. The pass may be run in a session of its own, on `main` (`AUTHORING.md`, “The language pass, in a session of its own”).
- **`scripts/merge-sources.mjs <book> <chapters… | page file name> [--write]`** gathers the proposed entries and reports what has to be settled by hand: a key already used for another page, one key proposed for two pages, one page under two keys. `--write` appends the rest to `content/sources.yaml`.
- **`.claude/workflows/propose-themes.js`** (`args`: `book`, `leads`, `model`): one Fable agent reads a finished book and proposes theme pages, writing `.cache/batch/<book>/reports/themes-fable.md`. `write-chapters` runs it with the book's last batch, passing the reviewers' theme leads, beside the illustration (`AUTHORING.md`, “Theme candidates at the end of a book”).
- **`scripts/codex-themes.mjs <book> [--model] [--force] [--print]`** has Codex review a finished book’s theme candidates, read-only: `STANDARDS.md` §8, `THEME-CANDIDATES.md`, the reviewers’ leads in `.cache/batch/<book>/theme-leads.md`, the brief and the chapters. It judges each candidate, proposes arcs of its own, and writes a ranked list (a handful as a rule, more for a big book) with a “Not recommended” section to `.cache/batch/<book>/reports/themes-codex.md` (skipped if that exists). `batch-finish.mjs` runs it when the batch has written the book’s last chapter, so it is ready while the author looks at the image (`AUTHORING.md`, “Theme candidates at the end of a book”).
- **`scripts/batch-notes.mjs <book> <the run’s journal.jsonl>`** reads the reviewers' results and appends the reader questions no source answered to `content/<book>/UNANSWERED.md` and the theme candidates to `THEME-CANDIDATES.md`; it prints anything a reviewer left for the author. The journal's path is in the Workflow tool's result (“Transcript dir”). **`scripts/batch-finish.mjs <book> <journal> <question prefix>`** runs it with the other after-batch steps (merge the sources, print the reviewers' questions for the coordinator to settle, commit the documents, `batch-commit.mjs`, and `codex-themes.mjs` when the book is finished).
- **Research scripts for the agents** (`scripts/source.mjs`, `scripts/footnotes.mjs`, `scripts/hebrew.mjs`; described under “Checks”): the writer, checker, reviewer, and auditor are told to read pages with `source.mjs --find` and not with `curl`, to start a chapter with `footnotes.mjs`, and to use `hebrew.mjs` for the Hebrew, so the pages a writer fetched are already cached when the checker and reviewer open them. The writer also finds KnoWhys with `knowhys.mjs`.
- **Scripts for the checker and the reviewer** (`scripts/ledger-context.mjs`, `scripts/check-sources.mjs`, `scripts/footnotes.mjs --compare`, `scripts/check-chapter.mjs`; described under “Checks”): the checker starts its source comparison from the output of `ledger-context.mjs` (and uses `source.mjs --find` only to read further), checks the proposed entries with `check-sources.mjs` (the writer and reviewer run it too), compares the notes with the Gospel Library with `footnotes.mjs --compare`, and every agent runs the checks with `check-chapter.mjs`, which adds the proposed entries in memory, so nobody makes a scratch copy of `content/` any more (`.claude/agents/chapter-*.md`, `.claude/workflows/write-chapters.js`).
- **`scripts/theme-dossier.mjs <book> <dossier path> --words "w1,w2" [--stem] [--hebrew H1,H2] [--verses "c:v,…"] [--site all]`** starts a theme page's dossier with what a script fills exactly: every occurrence of the words (and of each Hebrew word) in the text, the same phrases in every other book, the Church's heading, footnotes and *Scripture Helps* for each key verse's chapter, and what the site already says, each under the command that made it. The researcher starts from that file and fills the rest.
  For a volume's guide (`theme-dossier.mjs old-testament <dossier> --words "…" --verses "genesis 16:13,exodus 21:10"`) the words are searched in every book that has text and on the whole site, and each key verse names its book.
- **`.claude/workflows/write-guide.js`** (`args`: `owner`, `file`, `dossier`, `outline`, `writerModel`, `codexModel`) is the writing half of a guide: a `theme-writer` (Sonnet) writes the page, its ledger and its proposed sources from the outline and the dossier; a `theme-reviewer` (Opus) returns a verdict and required fixes; the writer makes them; then an Opus agent runs `codex-read.mjs` on the page and applies the findings that hold up, adding nothing. Each runs `check-page.mjs`. Research (one `theme-researcher` call) and the outline (the coordinating session's) come before it. Afterwards the coordinator runs `merge-sources.mjs <owner> <file> --write`, commits the page with its ledger, and shows it in the preview.
- **`.claude/workflows/write-theme.js`** (`args`: `book`, `file`, `dossier`, `outline`, `writerModel`, `codexModel`) is the same four steps for a theme page (the writer, the reviewer with the theme verdicts, the repairs, the language pass), with the page in `content/<book>/themes/` and its ledger under `evidence/themes/`; research and the outline come before it as for a guide, and afterwards the coordinator merges the sources, commits, and links the chapters with `link-theme.mjs`.
- **`scripts/link-theme.mjs <book> <chapter> <verse> "<note title>" "<sentence>"`** appends one sentence (the link from a chapter note to a theme page, `STANDARDS.md` §8, “The page links, it doesn't repeat”) to the end of that note's body without reformatting the file; it says so and changes nothing if the note is already linked.
- **Theme pages use the same scripts** (`STANDARDS.md` §8): the researcher starts from `theme-dossier.mjs` and `occurrences.mjs` and reads with `source.mjs`, `footnotes.mjs` and `hebrew.mjs`; the writer runs `check-content <book> <file name>` and `check-ledger <book> <file name>`; the reviewer runs those two first and reads only what the script can't judge (`.claude/agents/theme-*.md`).
- Then the checks (`check-content`, `check-quotes`, `check-ledger`, the build), and one commit per chapter with its ledger. `check-content` now also reports pointers to notes that aren't there, announced sources, outside commentary, and the length of `setting`; run it with `--repeats` over the whole batch to see passages that several chapters quote from the same source, which one explanation and a link may replace.
- **The book's illustration, once, with the last batch.** Pass `lastBatch: true` and `write-chapters` ends by running `create-book-art` if every reviewer reported its chapter ready; if not, its result's `next` says which chapters hold it up, and the coordinator runs `create-book-art` by name after the repairs. The result's `art.candidate` is the image Codex drew, for the author to see. The rest is the coordinator's and the author's (“Book illustration workflow” below). The build warns about a book whose chapters are all written and whose `visual.yaml` is missing, not yet approved, or names a missing file, so the stage can't be forgotten.
- **`scripts/status.mjs [book]`** prints where each book stands, from the files themselves: chapters written (a chapter with no `setting` is bare), ledgers, theme, guide and facsimile pages, `status: preview`, `visual.yaml`’s status, each volume's guides (with those still in preview or without a ledger), the question numbers under the book’s heading in `OPEN-QUESTIONS.md`, commits not on `origin/main`, and the chapters whose language pass a commit subject records (“<Book> <n>: language pass …”). No document repeats any of this (`AUTHORING.md`, “Status”).
- **`scripts/batch-usage.cjs <a Workflow run's transcript folder> [--calls]`** reports what a batch cost, from the agents' transcripts: for each role and model, a chapter's average steps, tool calls, tokens written, read new, sent again from the cache, and the session's size at the end; `--calls` adds which commands each role ran and how many characters each kind returned. It is how one arrangement is compared with the last (`AUTHORING.md`, “Plan for the next book”).
- **`scripts/preview-site.mjs [out dir]`** builds the site with preview books and pages and makes every link relative, once published to the claude.ai preview artifact, which was removed on 2026-10-16 (preview work is shown in the local preview, or on the dev site when the author asks: `AUTHORING.md`, “Showing a change”); kept for a relative-link copy of the site. It writes the site to `.cache/preview/dist` and the list of files to publish to `.cache/preview/files.json`. A live book's pages are left out and linked to the live site; `--keep genesis/guides/,isaiah/guides/` keeps the pages under those paths, for a change that alters a live book's page (a volume guide appears on every book's Guides page).

## Site design

Guide and theme source lists use small lowercase letters for links back to each citation (“↑ a b c …”; author, 2026-10-14, S7). Letters restart for each source and continue with aa after z. The shared renderer is `renderGuide` in `src/templates/pages.mjs`; `.backrefs` in `src/assets/site.css` styles them.

Citation numbers on guides and themes open a source popup on mouse hover, keyboard focus, or a tap/click (author, 2026-10-14). The popup shows the full citation, its source link and locator, and a link to the source list. Close it with its close button, Escape, or a click outside. `site.js` reuses `.reference-source` from the source list, so previews and the list agree; the native Popover API keeps it above the page without moving the reader. Browsers without popover support and readers without JavaScript keep the ordinary links to the source list. Single and multiple return links both retain letters at the author's request.

Scripture references use the same popup for the King James text of any verse or passage whose book is on the site, including a passage that runs into the next chapter (“Isa. 52:13–53:12”, marked where the chapter changes); a whole chapter (“Isa. 38”) has none (author, 2026-10-16: “I think this is a really good feature”). A long passage scrolls inside the popup, with a fade at the bottom until its end. `linkRefs` in `src/lib/refs.mjs` marks each reference with `data-scripture`, and `scripture-previews.mjs` puts the verses each page needs into the page. A mouse click goes to the chapter; on touch the first tap shows the preview and its heading goes to the chapter.

**Scripture popups throughout the site** (author approved, 2026-10-14): the shared layout embeds just that page's available references of one to three consecutive verses from the local scripture text (`src/lib/scripture-previews.mjs`, configured by the build). Longer passages, whole chapters, cross-chapter ranges, and books without local text retain their ordinary links. Mouse hover and keyboard focus preview the passage; clicking the original reference or pressing Enter follows its link. A touch or pen tap opens the preview, whose reference heading links to the chapter (author: clicking after hovering must not require moving the mouse). There is no separate “Open chapter” link. Pointer events distinguish touch from mouse on devices with both. The script also enhances references in expanded notes when those are inserted into the page.

Shared presentation components are in `src/templates/ui.mjs`: section navigation (`sectionNav` for a chapter's or book page's fixed sections; `headingNav` builds the same “Outline” bar from a rendered Markdown page's `<h2 id>` headings, so every guide page, every theme page (author, 2026-10-16) and the About page carry one), reading tools for chapters and facsimiles, note sources and the expanded-note dialog, and the search scope picker. Their styles live in `src/assets/site.css`; behavior lives in `src/assets/site.js`. Keep widths, spacing, and sticky offsets in CSS variables rather than page templates. The site header sticks to the top of every page, with the section navigator directly below it when present; on a page with the section navigator the header slides away while the reader scrolls down and returns on a scroll up, so only the navigator stays pinned while reading (author, 2026-10-16; `header-away` in `site.js`). Reading tools scroll normally. Measured header and section-navigation heights keep anchor targets and margin notes clear of both. Search uses the canonical volume/book and note-kind metadata and `bookAliases` from `src/lib/refs.mjs`, so navigation and reference searches share one book vocabulary. Parsed references prioritize matching verses and attached notes; word searches match titles and bodies, with the volume/book picker narrowing the scope. Note citations stay collapsible on screen and open temporarily for printing.

- **Margin notes.** On screens 880px and wider (an iPad mini held sideways qualifies; held upright it doesn’t), a note opens in the right margin beside the phrase that opened it, so the text never moves and the reader keeps their place. One note is open in the margin at a time: opening another shrinks the earlier ones to one-line cards (title and ×) that reopen on a tap, because a stack of full notes pushed some of them thousands of pixels from their phrases. A newly opened note slides up the margin if needed to stay on screen. Narrower screens keep the original behavior (notes open beneath their verses, as many as the reader likes). The layout is in `src/assets/site.css` (the `min-width: 880px` block; the notes column takes the room the window has to spare, 260–420px) and the positioning in `src/assets/site.js` (`layoutNotes`, `setNote`).
- **Touch targets.** On touch screens (`pointer: coarse`) every control a finger uses is at least 44px; small controls inside the text (verse numbers, markers) get an invisible larger hit area so the lines don't spread (the `pointer: coarse` block at the end of `site.css`).
- **Related switch.** A toolbar switch shows every note as a compact card (kind, title, and the note’s opening sentence, generated at build time by `teaser()` in `src/templates/chapter.mjs`). Cards sit in the margin on wide screens and under the verse on narrow ones; clicking a card or phrase expands that note and collapses the others. It is off for first-time visitors, and each reader’s choice is remembered. Because the card shows each note’s first sentence, open notes with a sentence that says what the note is about, not a hook like “This is the hardest line in the chapter.”
- **Section headings** (“Background”, “The thread through the chapter”, “In plain words”, and the rest) are defined once, in `SECTIONS` in `src/site.mjs`. Change one there and it changes on every chapter of every book and in the site’s own descriptions. Templates use `book.name`, never a hard-coded “Isaiah”.
- **Reading width:** one setting, `--read-w: 540px` in `site.css`, used by chapters, guides, and the About page (about 55 characters a line in chapters). The author reads mostly on an iPad mini, so check layouts at 744px (upright) and 1133px (sideways).
- **Coloured small text:** a colour used for small text anywhere on the site (a division's colour, the accent of citation numbers) is blended 30% toward `--ink` with `color-mix`, so it reaches 4.5:1 on the page; fills, rules and icons keep the colour itself (author, 2026-10-16: “It should apply everywhere on the site”). New styles follow the same rule. Two book colours still fall short, Malachi's and Mosiah's gold `#c9a227`, and the author chose to keep them.
- **Guides index:** a book's Guides page lists its own guides, then its themes, and never its volume's (author, 2026-10-18: “No book should inherit the volume guides.”); a book with no guide of its own has no Guides page and no Guides link (author, 2026-10-18: “If a book doesn't have guides, it does not inherit the guides from the volume. Just don't have guides for that book.”); the header's Guides link appears on a volume's pages when it has guides (`VOLUMES_WITH_GUIDES` in `src/site.mjs`). The list of guides and themes (`renderGuidesIndex` in `src/templates/pages.mjs`) is not running text, so it uses its own wider width (`.guides-wide`, 860px) with two columns of cards from 560px up (`.guide-cards-two`). The author preferred two columns to one (2026-10-01).
- **Scriptures menu.** The header's menu is always labeled “Scriptures” (`scriptureMenu` in `src/templates/layout.mjs`; behavior in `site.js`). It lists all five volumes of the standard works, always, and under each the books that are on the site. On screens 640px and wider it opens as one panel of three columns: volume, book, and a grid of chapter numbers (tinted when the chapter has commentary; dashed ones open the Gospel Library). The panel keeps its size, narrowing its columns a little below about 740px. With a mouse, pointing at a volume or book opens its column and clicking goes to its page; on a touch screen the first tap opens the column and a second tap goes to the page; the name at the top of each column also links there. Narrower screens show one column at a time with a back button. It opens where the page is (current volume, book, and chapter), closes on any choice, a click elsewhere, or Escape, and without JavaScript is a plain list. Beside it: Guides (on pages of a book that has guides), About (680px and up; in the menu on narrower screens), and Search. Each volume's color is a `--v-<volume slug>` variable in `site.css`.
- **Home page library.** The home page's library is the Scriptures menu's picker, open on the page (`.picker` in `renderHome`, `src/templates/pages.mjs`; drawn by `site.js` from the menu's data plus each book's `home.blurb`). It shows the five volumes, the books under the chosen one, and the chosen book's blurb, links, and chapter numbers, so it is the same size however many books there are. Here a click only selects; the names at the top of each column are the links. Under 640px it is a list of volumes and books, and a book opens its chapters in place. The reader's last book is remembered, and the chapter last opened is marked in it. Nothing on the home page names a particular book except the “Continue” line a return visit shows (below).
- **Home page notes.** “Try a phrase” shows three note cards, chosen at random when the site is built (`renderHome`). A quiet “Show three more” link under the cards (a button beside the heading stood out too much; author, 2026-10-03) replaces them with three others chosen in the browser (`site.js`). The build writes every note of every built book to `notes.json` at the site root, with only what a card needs (book, chapter, verse, id, kind, phrase, and the first 150 characters of the note); the page fetches it on the first click, not when it loads. The cards drawn in the browser have the same markup as the built ones; each kind's chip (icon and label) comes from a hidden `<template class="teaser-chip">` that `renderHome` writes from `KINDS`. Only notes with a phrase under 60 characters are drawn, the same rule the build uses. The button is hidden until `site.js` shows it, so without JavaScript (or if `notes.json` can't be fetched) the three built cards stay.
- **Book pages** show the book's guides and themes as cards after the chapters, each with its own entry in the section bar (`renderBookIndex` in `src/templates/pages.mjs`; author, 2026-10-15: “the book pages get rather long. I still think its the right thing to do”). Only the book's own: the volume's guides don't belong with them, though the book's Guides page lists them. The header has a Themes link beside Guides on every page of a book with themes (`layout.mjs`).
- **The home page's illustration** sits beside the heading and introduction on wide screens (860px and wider), filling their height and trimmed only on its left (`object-position: right`), and below them on narrower screens; 32px separate it from the library (author, 2026-10-16: “beside. left side trimmed. 32 px”). There are no buttons under the introduction (“Let's remove the buttons”).
- **A book page's illustration** sits whole beside the introduction on wide screens (860px and wider), at its own shape and never trimmed, since each book's picture places its things across the whole width; “What's in this picture” is listed open under it, its eye button turned into the list's heading (`site.js` keeps it open there). On narrower screens the picture runs full width under the introduction with the key behind the eye button. Every book page, by one rule in `site.css` (author, 2026-10-23, option E of a mockup of five: “this needs to be the look for all books”).
- **The home page remembers the chapter last opened on this device** (`lastRead` in local storage, set by every chapter page): a “Continue” line above the hero's buttons links to it, and the library picker opens on its book with the chapter marked (author, 2026-10-16: “I may be studying Isaiah 53 for several days in a row”). A first visit shows neither; nothing leaves the browser.
- **Volume pages.** `/old-testament/`, `/new-testament/`, `/book-of-mormon/`, `/doctrine-and-covenants/`, and `/pearl-of-great-price/` list that volume's books on the site first, as a list under the volume's divisions (`DIVISIONS` in `src/lib/canon.mjs`: the Law, history, poetry and wisdom, the major and the minor prophets; for the New Testament the Gospels and Acts, the epistles, Revelation), with headings only when the books fall in more than one, two columns on wide screens, and then the guides (author, 2026-10-16) and link to the volume in the Gospel Library. The five volumes are in `src/lib/canon.mjs`; a book's volume and its place in it come from its `abbr` and the scripture-reference table in `src/lib/refs.mjs`. Book pages link their eyebrow to their volume's page. A volume's introduction is the Markdown body of `content/volumes/<volume slug>/volume.md`, or of `content/volumes/<volume slug>.md` for a volume that has no directory yet, shown between the page's heading and its list of books (`renderVolume`); the five files exist as placeholders with no body (author, 2026-10-06: “We'll create the content later”), and a page with an empty file is unchanged. A volume's guides are listed on its page between the introduction and the books (“Volume guides,” below). The body takes `[[references]]` like any page; it has no `[@key]` citations or source list yet, so add those (as `renderGuide` has them) when the first introduction is written.
- **Search** has a volume-and-book picker; each `search.json` entry carries its book's or volume's slug in `b`. A volume selection includes its books and its own guides; volumes with guides offer a separate guides choice in the picker. A recognized book/chapter/verse reference puts that chapter or verse first, followed by notes attached to the requested passage. Result titles are the links. The original type filters and search-as-you-type remain, alongside a submit button.
- **No reading progress** (author, 2026-10-06). The “I’ve studied this chapter” checkbox, the marks on the chapter cards and the progress bar on book pages were removed: they were kept in the browser’s own storage, per device, which a browser may clear, and a tracker that can lose its record is worse than none. Don’t add one back without accounts and a server.
- **Words in another language** stay in italics; the author considered a color for them and decided against it (2026-10-03).
- **Highlighted phrases** are `<span role="button" tabindex="0">`, not `<button>`, so they wrap across lines like ordinary text; `site.js` gives them Enter and Space.
- **Last-revised labels.** Chapter, guide, theme, and About pages show a quiet date below the page introduction. During the build, `build.mjs` reads the last Git commit that changed that page’s own source file (falling back to the file timestamp only in a source archive without Git history). This is a content date, not the date of a site-wide deployment.

### Reading offline

(Author, 2026-10-15: it must work on an iPad, an iPhone and a Mac, and on any other device if it can.) A reader can save the whole site on a device from the About page's “Reading offline” section (the footer's “Read offline” link goes there; author, 2026-10-16: not front and center, so no separate page and nothing in the header) and then read every page, note, guide and search without a connection. It is an installable web app with a service worker, chosen over a zip of pages (an iPad can't browse a folder of linked pages), a native app (a developer account, App Review, a release for every change, and Apple devices only) and an e-book (no margin notes, popups or search).

- **On deployment** the build writes `offline.json`: every file of the site with its URL and a hash of its contents (`writeOfflineList` in `scripts/build.mjs`; a page's `?v=` stamp is left out of its hash, so a deploy that changes nothing re-fetches only the home page, whose teasers are random). `public/sw.js`, `public/manifest.webmanifest` and the Home Screen icons (`public/icon-180.png`, `icon-512.png`, drawn from the favicon) are copied as they are.
- **On the device nothing happens until the reader asks.** The About page places the Save button where `content/about.md` has `<!-- offline -->` (`offlinePanel` in `src/templates/pages.mjs`), and `site.js` installs the service worker only when it is pressed; a reader who never presses it has none, and “Remove the saved copy” deletes the copy and uninstalls the worker. “Save for offline” fetches every file in the list into one cache, six at a time, and stores the list last, so an interrupted save finishes on the next press. After that, any page opened with a connection asks for an update at most once a day, and only files whose hash changed are fetched; files gone from the list are deleted.
- **Pages still come from the network first** (with a 4-second wait), the stylesheet and script too, so a saved copy never hides a newer page; the copy answers when the network doesn't. Fonts and images come straight from the copy. A page that isn't saved, offline, gets the saved `404.html`.
- **Size.** About 67 MB on the device and about 20 MB to download (pages and data are compressed in transit), most of it the HTML of the chapters (Psalms alone is 16 MB, because each page carries its scripture popups). The book illustrations are JPEGs for this reason (`book-art.mjs approve` saves them so); as PNGs they were 37 MB of a 100 MB copy.
- **Devices.** On an iPad or iPhone the copy should be saved from the Home Screen app (Share → Add to Home Screen): Safari may clear a site's data after about a week without a visit, but not a Home Screen app's, and the two keep separate copies. On a Mac, Safari's File → Add to Dock, or Chrome's or Edge's Install; Firefox keeps the copy in a tab. The About section gives the reader one line for each kind of device (author, 2026-10-16: “platform agnostic”); Chromium reports the site installable (`Page.getInstallabilityErrors` is empty). Links that leave the site (the Gospel Library, sources, unwritten chapters) still need a connection.
- **When the site changes shape** (a new kind of file, a page moved), nothing here needs to change: the list is every file the build writes, except `sw.js`, `offline.json`, the sitemap, `robots.txt` and the manifest (`OFFLINE_SKIP`). After a change to `sw.js`, the About section's controls or the build's list, run `npm run build && node scripts/test-offline.mjs`: it saves the copy in Chromium, then stops its server (Playwright's offline switch doesn't reach a service worker's requests, so it can't be trusted for this) and opens pages, an illustration, the fonts and search with no network, then removes the copy. It needs Playwright, which is not among the project's dependencies. Then try it once on a real iPad.

## Books

The build treats every directory `content/<slug>/` that has a `book.yaml` and a `chapters/` directory as a book, and builds each under `/<slug>/`. `src/lib/books.mjs` does the discovery (the build and the scripts share it); `LIBRARY` in `src/site.mjs` is the list of books that templates read (header nav, 404 redirects, internal `[[…]]` links). Everything Isaiah-specific lives in `content/isaiah/book.yaml`. Scripts take the book as an optional first argument (`node scripts/show.mjs jeremiah 1`, `node scripts/check-quotes.mjs jeremiah 1`), defaulting to `isaiah`. `scripts/fix-yaml.mjs` with no arguments still touches Isaiah only; `npm run build` runs it with `--all`. `BUILD_OUT=<dir>` makes the build write there instead of `dist/` (for agents that run the build as a check at the same time). For comparing two builds byte for byte, `BUILD_VERSION=x BUILD_SEED=1 node scripts/build.mjs` pins the `?v=` stamp and the home page's random teasers.

**Preview and live.** A book whose `book.yaml` has `status: preview` is built only by `npm run dev`, `PREVIEW=1 npm run build`, and a Cloudflare build of any branch but `main` (the dev site); the live build leaves it out completely. With no `status`, a book is live.

**A book of one chapter has one page** (author, 2026-10-24: “Single page.”, after a mockup of Obadiah). Its chapter is built at the book's address, `/<slug>/`, with the book's name as the title, the chapter's title under it, and the approved picture with its key below the hero's details (beside them on a wide screen, as on a book page); there is no book page, division map, chapter dial, breadcrumb or pager, and the book's `coreSources` join the chapter's Sources. `/<slug>/1/` is a page that forwards there, keeping the `#v…` anchor. `chapterPath` and `singleChapter` in `src/templates/chapter.mjs` decide it (from the number of chapters in `data/kjv/<slug>.json`); `refs.mjs` links `[[Obad. 1:3]]` to `/obadiah/#v3`, and the Scriptures menu's chapter cell goes to `/<slug>/`. The book's `intro`, `heroQuote`, `divisions` and `beloved` are not shown for such a book; anything only the intro said belongs in the chapter's `setting`. Obadiah is the first; Philemon, 2 John, 3 John and Jude will be the same.

**Unwritten chapters.** A chapter with no YAML file is unwritten. It gets no page and is left out of search and the sitemap. On the book page its card is greyed out and opens the chapter in the Gospel Library; the chapter strip dims its tick and links there too; previous/next links skip it; `[[Jer. 5:1]]` links to the Gospel Library until the chapter is written (`LIBRARY` carries each book's written chapters for `src/lib/refs.mjs`); and `404.html` sends `/jeremiah/5/` to the Gospel Library. The home page card and the header menu say “N of 52 chapters” until the book is complete.

**The chapter's introduction** (`introSection` in `src/templates/chapter.mjs`): Background and the thread are `<details>` sections, open by default, and a reader who closes one keeps it closed on every chapter (`collapsedIntro` in `site.js`). Both show only their first paragraph until “Continue reading” is pressed (`data-preview`; the thread since 2026-10-13, at the author's request, “like the Background section”).

**Bare chapters** (author, 2026-10-07). A chapter file may hold only `chapter`, `title`, `tagline`, `when`, `notes`, `parallels` and `sources`: the page then shows the whole text as one passage with its notes, and no Background, thread, plain-words or closing sections (the template leaves out whatever is missing). It is for commentary written under one book that belongs under another not yet written: the note moves to its own verse, and the chapter is written in full later. The file begins with a comment saying it is bare, and the book's brief lists its bare chapters. To the build it is a written chapter. Mosiah 12 and 15 are the first (`content/mosiah/BRIEF.md`).

**Facsimiles** (2026-10-07; the author approved the shape the same day: “I like the shape. Looks good”). A book with `data/kjv/<slug>.facsimiles.json` and `content/<slug>/facsimiles/<n>.yaml` gets a page per facsimile at `/<slug>/facsimile-<n>/` (`src/templates/facsimile.mjs`): the plate, then its explanation set out like a chapter's verses, one numbered figure to a line, so a note opens on a phrase of the explanation as it does on a phrase of scripture (`notes`, with `ref` the figure's number; the note markup and the margin layout are the chapter's own). The JSON holds the explanations in the 1921 edition's wording, read by eye from the scan, with `differs` where the current edition reads otherwise; the YAML holds `with` (the chapter the plate goes with, which gives the page its color and the chapter a link to it), `title`, `tagline`, `image` (in `src/assets/facsimiles/`, cropped from the same scan), `alt`, `credit`, `about`, `notes`, and `sources`. The book page lists them under “The facsimiles” (`facsimilesBlurb` in `book.yaml`). A page's ledger is `content/<slug>/evidence/facsimiles/<n>.yaml` (`where` is `about` or `note fig. <n> “<title>”`), and `node scripts/check-ledger.mjs <book> facsimiles` confirms its quotes; the build warns about a note's phrase that is not in its figure, an unknown kind, a note on a line with no number, and an unknown source key. Not done: `check-content`, `check-quotes`, `ledger-context`, `check-sources` and `check-chapter` do not read these pages (the checker did their work by hand), `[[…]]` cannot link to one (a note links with `[Facsimile 1](/abraham/facsimile-1/)`), and the Scriptures menu does not list them.

Markdown files at the top of a book's directory (`BRIEF.md`, `THEME-CANDIDATES.md`, and so on) are project notes; the build ignores them. Markdown in `guides/` and `themes/` is published.

**Volume guides** (author, 2026-10-12: a guide belongs to the volume when its content is true of more than one book). A volume is a directory too, `content/volumes/<volume slug>/`: `volume.md` (its introduction), `guides/NN-slug.md`, `evidence/guides/NN-slug.yaml`, and project notes at the top, which the build ignores (`GUIDES.md` holds the author's decisions about the Old Testament's guides). The five volumes are fixed (`src/lib/canon.mjs`); `discoverVolumes` and `findOwner` in `src/lib/books.mjs` return one as an *owner* of pages (`kind: 'volume'`, `slug`, `name`, `dir`, `hasGuides`), so the scripts that take `<book>` for a page take `old-testament` as well: `check-content`, `check-ledger`, `check-quotes`, `check-page`, `check-sources`, `merge-sources`, `ledger-context`, `codex-read`, `occurrences --site`, `theme-dossier`, `status`. A volume guide is built by the template a book's guide uses (`renderGuide` and `renderGuidesIndex` take an `owner`), at `/<volume slug>/guides/<slug>/`, and is listed on the volume's page, on `/<volume slug>/guides/`, and on no book's Guides page. A chapter links to a section of one as to any page: `[the bride-price](/old-testament/guides/women-and-marriage/#bride-price)`.

**A two-sided timeline** (`.tl-figure` in `site.css`, used by the Old Testament guide *Israel's Story in One Place*): an `<ol class="tl">` of `<li class="tl-l">` (Israel) and `<li class="tl-r">` (the nations), each with a `.tl-date` pill on the central rail and a `.tl-text`; `<li class="tl-era">` labels a band. The figure breaks out to 820px and becomes one column under 600px. It is the style for every volume's timeline (author, 2026-10-13; the Book of Mormon, the Doctrine and Covenants and perhaps the New Testament are to have one).

**Maps** belong to the volume, so that every guide of every book in that period can show the same one: `content/volumes/<volume slug>/maps/<name>.svg`. **`scripts/map.mjs <volume> <name>`** draws it from `<name>.yaml` beside it (the area as `box: [west, south, east, north]`, the width, the places, and labels for regions, seas and rivers; its header says each field) with public data: Natural Earth (public domain) for land, lakes, rivers, deserts and mountain ranges, and OpenBible.info's Bible Geocoding Data (CC BY 4.0, credited in the map's corner) for each place at its modern identification. The data is fetched once into `.cache/geo/` (the script's header gives the five files and where they are), not kept in the repository; the SVG is committed. The drawing uses the classes of `.map` in `site.css` (`m-land`, `m-sea`, `m-desert`, `m-mountain`, `m-lakefill`, `m-river`, `m-city`, `m-home`, `m-region`, `m-empire`, `m-river-label`, `m-credit`), so it follows the light and dark themes. A guide shows a map with `<!-- map: old-testament/two-kingdoms-and-assyria -->` on a line of its own inside its own `<figure class="map-figure">`, with its own `<figcaption>` (and so its own citations; a link in the caption is written as `<a href>`, since Markdown inside an HTML block is not parsed). `embedMaps` in `scripts/build.mjs` puts the drawing in before the page is rendered and warns when a named map is missing. Check a map by looking at it: the labels are placed by hand in the spec (`dx`, `dy`), and crowded places need nudging. **A chapter's map** (a mockup on the branch, 2026-10-22): `map.mjs` also writes `<name>.places.json`, for each place the verses where OpenBible's ancient-places data (`openbible-ancient.jsonl`, fetched into `.cache/geo/` with the others) says the King James text means it, and the first sentence of its Bible Dictionary entry (read with `readPage`; `bd:` gives another entry's address, `bd: none` none; an entry with several senses gives the one about a place). A place whose OpenBible name differs gives `ancient:` (a list where OpenBible splits one place, as Beersheba); books OpenBible doesn't cover are searched by name (`scan: [abraham]`, a place's `also:` and `skip:`). The build turns the verses into chapters (`mapPlaces`), and a guide opened from a chapter's Context link (`?from=genesis/28`) shows the places that chapter names and lists them under the map; tapping a place shows its sentence and every chapter that names it (site.js “chapter map”). **`scripts/map-coverage.mjs [map name …]`** says how well a period's map serves its chapters: how many light a place, which don't, and the places they name most that the map lacks ("no location" where OpenBible has none); run it after changing a map's spec.

**A page in preview.** A guide or theme page whose front matter says `status: preview` is built only with `PREVIEW=1`, as a book in preview is: the live build leaves out the page, its card, its search entry and its place in the sitemap. A new page for a live book or a volume starts so, is committed to `main` like any content, and goes live when the author has read it and the line is removed.

### Adding a new book

The author's brief for the book comes first (see `AUTHORING.md`). For a Book of Mormon book, read “Notes waiting for a Book of Mormon home” in `OPEN-QUESTIONS.md` first: commentary written under Isaiah that moves to the new book when it is set up. Then:

1. `node scripts/fetch-kjv.mjs Jeremiah` writes `data/kjv/jeremiah.json` (the source file name has no spaces, such as `1Samuel`; a second argument sets a different slug). Then run `node scripts/check-kjv.mjs <slug>`, which lists every verse that differs from the Gospel Library edition (spellings, hyphens, punctuation, and LORD or GOD in small capitals); add the differences to `LDS_SPELLINGS` in `fetch-kjv.mjs` and import again until it reports none.
   A book that is not in the King James Version (the Book of Mormon, the Doctrine and Covenants, the Pearl of Great Price) is imported from the Gospel Library instead: `node scripts/fetch-gl.mjs moses pgp/moses 8` (slug, Gospel Library path, number of chapters) writes the same file, `data/kjv/<slug>.json`, and `check-kjv` then reads the pages again and should report no difference. Moses was the first (2026-10-06). **The text of every book is to be a public-domain edition’s** (author, 2026-10-06): the Church’s current editions are copyrighted, so for a book outside the King James Version find a printing published before 1931 (archive.org has plain-text scans; the 1921 Pearl of Great Price is `pearlofgreatpric0000jose_d8d6`), then run `node scripts/find-verses.mjs <book> <scan.txt> [more scans]`, which says which verses are found word for word in the scans, and `node scripts/compare-edition.mjs <book> <scan.txt> --from <line> --to <line>`, which prints the words that differ verse by verse (scan errors show as differences, so the list is read by a person). The scans are too rough to import as the text; the import from the Gospel Library is corrected to the old edition’s wording instead: list each differing reading in `data/kjv/<slug>.edition.json` (`ref`, `current`, `edition`; `moses.edition.json` is the model), and `fetch-gl.mjs` applies them after importing while `check-kjv.mjs` puts them back before comparing, so it still checks every other word against the Gospel Library. Only wording is compared, not punctuation or capitals. Short quotations of the Church’s modern material (chapter headings, footnotes, *Scripture Helps*) stay as they are: the author counts them fair use (2026-10-06). Name the edition in the footer (`src/templates/layout.mjs`). `scripts/hebrew.mjs` has nothing for such a book, and `scripts/footnotes.mjs` looks for the *Scripture Helps* on Moses and Abraham in the Old Testament volume.
   **Psalms has two things no other book has** (author, 2026-10-10, of showing the titles: “just go do it”). `node scripts/fetch-psalm-titles.mjs` writes `data/kjv/psalms.titles.json` from the Gospel Library pages: the title above each psalm that has one (116 of them) and the Hebrew letters that head the stanzas of Psalm 119. The build reads the file if it is there; a chapter page shows the title before verse 1 as verse 0 (`<p class="verse psalm-title" id="v0">`), a note with `ref: 0` hangs on its words, and the search index has it. `fetch-kjv.mjs` does not touch the file, so importing the text again keeps it. And `unit: { singular: Psalm, plural: psalms }` in `book.yaml` makes the pages say “Psalm 23 of 150,” “Seeing Christ in Psalm 23” and “The psalms” where another book says “Chapter” and “chapters” (`chapterLabel` and `unitPlural` in `src/templates/chapter.mjs`); the Scriptures menu still says “chapters.”
2. `content/<slug>/book.yaml`, starting with `status: preview` (remove it when the book should go live; see “Preview and live” above). Required: `name`, `slug` (the directory name), `order` (nav and home-page position; lowest first), `abbr` (the abbreviation `src/lib/refs.mjs` uses, such as `jer`; `[[Jer. 1:5]]` links to the book from then on, and it decides which volume the book is listed under and where), `gospelLibrary` (path under `…/study/scriptures/`, such as `ot/jer`), `eyebrow` (line above the title, such as “The Old Testament”; it links to the volume's page), `heroQuote` (`text`, `cite`), `description` (meta description of the book page), `divisionsBlurb` (subtitle of the division map), `home` (`blurb`, the one-line description in the home page's library and on the volume page), `intro` (ending with one sentence that points to the sections of the volume's guides that hold the book's background, as every book page does from 2026-10-15: “For the wider setting of …, see [A Timeline of the Old Testament](/old-testament/guides/israels-story/#two-kingdoms)”), `divisions` (each `key`, `range`, `name`, `blurb`, and a `color`), `beloved`, `coreSources`, and optionally `rangeSources` and `titles`. `content/isaiah/book.yaml` is the model.
3. Division colors: each division gets `color` and, for dark mode, `darkColor` (defaults to `color`). The build appends them to `dist/assets/site.css` as `--div-<key>` variables; it warns when a division has neither a `color` nor a variable in `site.css`. Isaiah’s colors stay in `site.css` (moving them would change its output). The variables are global, so **give a new book’s division keys names that Isaiah doesn’t use** (`judah`, `nations`, `apocalypse`, `woes`, `hezekiah`, `comfort`, `servant`, `zion`).
   **An Old Testament book names its chapters' periods** in `book.yaml`, so each chapter's Context link opens its period guide (`content/volumes/old-testament/periods.yaml`; `content/volumes/old-testament/CONTEXT.md`): `periods:` as chapter ranges (`- { chapters: 1-5, period: babylon }`; a book may span periods, as Daniel does), and `noPeriod:` for chapters that have none, with why (`- { chapters: 1-11, why: before the patriarchs }`). The build warns about an Old Testament chapter that has neither.
4. Chapters in `content/<slug>/chapters/NN.yaml`; guides and themes as Markdown in `guides/` and `themes/`. A chapter with no file is unwritten (see above); `titles` in book.yaml can give unwritten chapters a title on the book page.
5. Book of Mormon comparison data is optional: `data/bom/<slug>-parallels.json`, same format as Isaiah’s (only Isaiah has one; `scripts/fetch-bom-parallels.mjs` is Isaiah-specific). Without it, chapter pages simply have no BoM panel.
6. Still written by hand for now: site-wide wording that names books (`SITE.description`, the 404 page’s Isa. 30:20 line, the search box’s example searches).
7. When the last chapter has passed review, the book's illustration (“Book illustration workflow” below). Don't write `content/<slug>/visual.yaml` by hand at the start: the book page shows the placeholder art until an approved one exists.

### Book illustration workflow

Every completed book gets one full-width landing-page illustration. This is an **AI authoring stage**, after all its chapters have passed review, and never part of the site build. The coordinator runs `.claude/workflows/create-book-art.js` (`write-chapters` runs it at the end of a book's last batch, when called with `lastBatch: true`). It has two steps:

1. **Direct.** `book-art-director` reads the finished book and saves its summary, motifs, composition, and proposed alt text in `content/<book>/visual.yaml` with `status: proposed`.
2. **Generate.** `node scripts/book-art.mjs generate <book>` builds the prompt from `content/visual-style.yaml` (the permanent visual identity) and that brief, and runs `codex exec`, whose built-in image tool draws one candidate. The script copies it from Codex's own folder (`~/.codex/generated_images/`) to `.cache/book-art/<book>/candidate-N.png`, which is not committed. Codex is run read-only and writes nothing in the repository. It needs the `codex` CLI signed in (`codex login status`), no API key. That tool takes no pixel size: at 16:9 it returns 1672×941, the size of every book image on the site, which the author accepts. If Codex answers that its model is at capacity, run it again or pass `--model <another Codex model>` (`codexModel` in the workflow's `args`). `node scripts/book-art.mjs prompt <book>` prints the prompt without drawing anything. Run `generate` again for another candidate, after editing the brief if the idea should change. `generate` redraws the whole scene, so when the author likes a candidate but for one thing, `node scripts/book-art.mjs edit <book> --from <candidate.png> --change "<the one change>"` gives Codex that candidate as its input and asks for only that change (author, 2026-10-23, after a request to shrink Zechariah's lampstand redrew everything: “Just shrinking the lamp and keeping everything else the same would have been perfect”); it saves the next `candidate-N.png`. The site’s style rule allows no people; a brief may carry `figures:`, one sentence saying which small figures the author has allowed for that book, and it then replaces that rule in the prompt (first used for Moses, 2026-10-06: Adam and Eve, tiny and seen from behind). A brief may also carry `look:`, one paragraph naming the medium for that book alone; it replaces the site's style in the prompt and leaves out the site's rules that require a drawn, poster-like image (first used for Exodus, 2026-10-12, when the author found the house style “too cartoonish” and said he might be “shifting more toward photo-realism”; `content/visual-style.yaml` itself is unchanged until the author says so).

The author reviews the candidate. Only after approval does the coordinator run `node scripts/book-art.mjs approve <book>` (the newest candidate, or `--from <file>`; `--force` to replace an existing image), which saves it as a JPEG at `src/assets/<book>-book-art.jpg` (a tenth of the PNG’s size, made with `sips` on a Mac or ImageMagick elsewhere) and sets `asset` and `status: approved` in the brief. Then trim the brief's `motifs`, `composition`, and `alt` to describe the image that was kept (ideas tried and dropped along the way don't stay in an approved brief), and build the site. Then write the brief's `key`, “What's in this picture” (author, 2026-10-13: “One thing I really struggle with is seeing symbols in someone else's artwork. I don't want someone to struggle with that”): one line for each thing that is actually in the approved image, in plain words, saying which verse it shows, with the verse quoted exactly and its `[[reference]]`; a bold opening names the thing as the reader sees it. Look at the image itself, not only the brief, since an image can leave a motif out or add one. Check every quotation against `data/kjv/<book>.json`, have Codex read the list (`codex-read.mjs --file`), and build. The book page shows it under the image, behind a faint eye icon in the image's lower right corner (`artFigure` in `src/templates/pages.mjs`, `.art-key` in `site.css`, and a few lines in `site.js` that keep the icon on the image while the list is open). The renderer reads approved briefs automatically, so a new book never needs a book-specific template edit. Until a finished book has an approved brief whose asset exists, the build warns and the book page keeps the placeholder art.

## Reviewing the instructions

The instruction files (`CLAUDE.md`, `AUTHORING.md`, `STANDARDS.md`, `DEVELOPMENT.md`, the agent and workflow files) grow a line at a time, and what was true when a line was written stops being true. A review on the most capable model is worth its cost now and then, and not on a calendar: `node scripts/status.mjs` ends with how many commits have touched these files since the last review, how much they have grown, and how many chapters have been written since, and says when a review is due (40 commits, a quarter in size, or 50 chapters). After a review, tag it: `git tag review-YYYY-MM-DD`.

The review's checklist, so that it starts from the same questions each time (first run 2026-10-11, on Fable; it found a dead script reference, a script whose purpose had ended, a README three books out of date, the scripts documented in four places, and the standard being read whole by agents that needed half of it):

1. `node scripts/check-docs.mjs` first: stale references are mechanical.
2. For each document, what it says that is no longer true: a file, section, environment or step that no longer exists; a “not yet” that has since been done; a rule for a situation that no longer arises.
3. What is said in more than one place (a script's options, a process's steps, a rule restated in an agent file), and which one place should hold it.
4. What each agent reads before working, in kilobytes, against what its role needs.
5. What an agent does by hand that a script could do exactly (`AUTHORING.md`, “Offload to scripts what a script can do exactly”), from the last batch's `batch-usage.cjs --calls` output.
6. Incidents recorded as stories where a one-line rule would do (`AUTHORING.md`, “Lessons for the coordinator”).
